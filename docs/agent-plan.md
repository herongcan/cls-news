**整体四步**

| Step | 做什么 | 状态 |
|---|---|---|
| Step 1 | 模板分析入口，**不用 tool calling**：SQL 预筛 → 分类合并 → 打分打包 → 单次生成 → 引用校验 | ✅ **已收口**：S1.1–S1.5 全绿，195 测试 |

| Step 3 | 上下文记忆：会话级（「那第二条呢」）+ 任务级（「盯住半导体」），先不上向量库 | 未排期 |

Step 1 内部拆五个小步，每步都能独立验：

| 小步 | 内容 | 状态 |
|---|---|---|
| S1.1 | 建表 + 分类与合并（剔除导流、合并行情播报）+ 打分与分层打包 | ✅ 2026-11-27 |
| S1.2 | 模板解析 + 单次生成 + 引用校验 + guard（含主题校验）+ 配额 + `full` 策略 | ✅ 2026-11-27 |
| S1.3 | 并发单飞（A + B）+ `delta` 增量策略 | ✅ 2026-11-28 |
| S1.4 | 四个接口 + 浮层（主线首屏 / chips / 关键词框） | ✅ 2026-11-28 |
| S1.5 | 文档、`/api/agent/health`、CI 补一条 | ✅ 2026-11-28 |

**逐项的完成标志、实际交付文件、剩余待办，全部在 §13。**

Step 1 的验收一句话：点「今日热点」→ 3–5 条主线、每条引用都能回查到原文；点「A 股异动」→ 材料不足就直接拒答，且 `tokens_in = 0`。

为什么可观测性（`agent_run` / `agent_step`）不单列一步，而是并进 S1.1 的建表：Agent 出问题从来不是"报错"，是"它悄悄调错工具、拿到空结果、然后编一个答案"。没有执行链回放就调不出来 —— 这件事必须和第一行业务代码同时落地，排到后面等于放弃排查能力。

为什么 RAG 不在四步里：你的新闻是**结构化**的，`LIKE` 在精确匹配上比向量召回更准。RAG 唯一值得做的场景是语义召回（「找所有关于产能过剩的讨论，但文中没出现这四个字」），不是给简历加标签。见 §14。

## 0. 一句话结论

**不做通用聊天机器人，做一个「模板驱动、只答库内、每次花钱都要用户亲手点」的分析入口。**

形态是：**一个浮层、N 个模板、一套「SQL 预筛 + 单次生成 + 引用校验」**。模型只被调用一次，检索的决策权在代码里，不在模型里。

省钱靠三道闸，顺序是递进的：**缓存**（数据没变，0 成本）→ **增量**（只多几条，省 40%）→ **全量**（新增太多或不划算时）。详见 §10。

## 1. 为什么不是"接个 LLM 聊天框"

### 1.1 单条分析已经把"利好利空"答完了

现有 `prompts/analyze-news.md` 的输出字段：

```
sentiment（bullish/neutral/bearish）· confidence · summary
sectors[] · inference · stocks[]（market/code/name）
```

并且带硬性门槛：单一品种日内涨跌 ≤2% 判中性、摊薄类不给 bullish、传导只允许一层。  
也就是说「这条是好是坏、影响谁、力度多大、依据是什么」四个问题**已经答了**，再问一遍等于重复付费。

### 1.2 单条答不了、只有 Agent 能答的，只有四类

| 问题                   | 需要什么      | 现状                    |
| -------------------- | --------- | --------------------- |
| 同类事件最近发生过几次，这次更重还是更轻 | 跨条检索 + 计数 | ✅ 回购 36 条、半导体 27 条可支撑 |
| 今天同板块还有哪些消息，拼起来是什么图景 | 当日全量      | ✅ 日均 88–241 条         |
| 这条是新消息，还是旧闻重提 / 预期兑现 | 历史相似标题    | ⚠️ 需要模糊匹配，LIKE 不够     |
| 后续该盯什么               | 纯推理       | ✅ 能答，但不可验证，容易空泛       |

**答不了的（必须写进能力边界）**：涨没涨、是否已 price in。库里 1137 条全是文本，**没有任何行情/指数数据**。

### 1.3 数据现实（2026-11-27 实测）

| 指标          | 数值                                                                 |
| ----------- | ------------------------------------------------------------------ |
| 总条数         | 1137                                                               |
| 有数据的天数      | 8 天（11-11/12/13/16/21/22/23/27，中间 4 天为空）                           |
| 日均          | 约 142 条                                                            |
| 平均正文长度      | 171 字（最长 2336）                                                     |
| 今日（11-27）   | 88 条、1.79 万字符、≈ 1.05 万 token                                       |
| 最忙一天（11-16） | 241 条、4.84 万字符、≈ 2.85 万 token                                      |
| 已分析 / 待分析   | 130 / 1001                                                         |
| 关键词命中（全库）   | 涨停 47、回购 36、半导体 27、英伟达 21、美联储 14、光伏 12、大涨 9、军工 4、**暴跌 1**、**降准 0** |

两个直接后果：

1. **纵向对比只在热门题材上成立**，冷门词几乎必然"没找到"。功能必须配明确的失败话术，否则用户以为坏了。
2. **1001 条未分析**。让模型读未分析的内容时，返回值里必须显式给 `analysis: null`，否则它会自己编一个结论。

## 2. 三条不可协商的原则

### P1｜花钱的调用必须由用户动作触发

| 场景          | 是否花钱 | 处理                  |
| ----------- | ---- | ------------------- |
| 打开首页 / 浮层   | ❌    | 只读缓存，绝不调模型          |
| 点「生成主线」     | ✅    | 点击前显示预估 token 与剩余次数 |
| 发送一句提问      | ✅    | 同上                  |
| 点「展开」追问     | ✅    | 同上                  |
| 缓存命中        | ❌    | 标注"何时生成、数据有无新增"     |
| 定时任务 / 后台预热 | ❌    | **不做**              |

代码层硬拦：`AgentService.start()` 首行校验 `actor != null && trigger == "user"`，否则抛异常。这比写在文档里可靠。

> 这不是新约束，而是把现有 `app.analysis.auto=false` 的取舍（yml 注释："全自动等于把没人在意的那一半也送去模型"）延伸到 Agent 层。

### P2｜只答库内，引用必须可验证

1. 输出中的 `[[id]]` 与本次候选集求交，不在集合内 → 丢弃并记 `fabricated_citation`。
2. `refs` 为空的结论 → 整条丢弃，宁少不多。
3. 越界问题（预测涨跌、荐股）→ 固定话术，**不调模型**。
4. 时间窗自动扩展要明示："今日 0 条，已扩到近 3 天（共 6 条）"，不静默扩。

### P3｜前提不足就拒答，不编

典型反例：**"今天 A 股暴跌的原因分析"**。全库只有 1 条含"暴跌"，且没有指数数据。若不加保护，模型会拿训练知识编一个很像样的原因。  
所以每个模板必须有 `min-hits` 前提检测，不达标直接返回固定话术，**且不产生任何 token 消耗**。

## 3. 为什么 Step 1 不用工具调用

"工具"这个词在三个层次上被混用，先分开：

| 层                                   | 是什么                                 | Step 1          |
| ----------------------------------- | ----------------------------------- | --------------- |
| 服务端 SQL 预筛                          | 按时间窗 + 关键词查 `news` 表                | ✅ 用，但**不是工具调用** |
| 应用内 function calling                | 把工具 schema 给模型，收 `tool_calls` 再执行回灌 | ❌ 不用            |
| MCP server（`tools/mcp/cls-mcp.mjs`） | 给 Codex / Claude 等**外部** Agent 用    | ❌ 不参与，保持原样      |

### 3.1 日级全量注入装得下

| 场景           | 字符        | token       |
| ------------ | --------- | ----------- |
| 今日 88 条      | 1.79 万    | ≈ 1.05 万    |
| 常规日 78–105 条 | 1.8–2.1 万 | ≈ 1.1–1.3 万 |
| 最忙 241 条     | 4.84 万    | ≈ 2.85 万    |
| 满负荷 600 条    | 12 万      | ≈ 7 万       |

折算口径：中文约 1.7 字 / token。600 条也在 128k 窗口内，但会同时踩成本、延迟、注意力稀释三个坑，所以实际采用**分层打包**（见 7.4）。

> **实测修正（S1.1 落地后）**：分层后不是 1.8 万，是 **2.5 万**。原来这个数只用 8 个字符算行前缀，而真实一行是 `[[1312]] 11-27 14:32 标题` —— 光前缀就 17 字。按真实口径重算，600 条是 24.5k，常规日 119 条约 0.94 万（见 7.5 实测表）。

### 3.2 换来的四个好处

- **成本可预测**：token = 候选条数 × 平均长度，点之前能算给用户看。
- **可测试**：一条 SQL + 一次调用，假模型能跑完所有分支，不需要模拟多轮 `tool_calls`。
- **不会跑偏**：模型没有"再搜一次"的权力，不会出现"搜 5 次没找到最后编一个"。
- **代码少一半**：`AgentLoop`、`ToolRegistry`、并行 tool_calls、无进展检测全部不需要。

### 3.3 代价与引入时机

代价：**模型不能自主扩大检索范围**。问"跟三个月前比呢"，这版只会按模板时间窗查，查不到就说查不到。

引入 tool calling 的唯一判据：**问题本身决定了要查什么，且事先算不出要查几次**。典型就是自由提问里的"追溯对比"。这在 Step 2 才出现。

扩展路径是平的：接口不变，`kind='template'` 走单次，`kind='research'` 走循环，前端无感。

## 4. 产品形态：一个浮层，N 个任务

现有 UI 只有一页（`pages.json` 单页面、无 tabBar、卡片内联渲染分析），**没有详情页**。所以入口必须挂在现有结构上，且不新增路由。

```
┌─────────────────────────────────────┐
│  今日主线                     [更新] │ ← 缓存命中是「已最新」并置灰；没结论才是「生成」
│  16:20 生成 · 88 条 · 5 条主线      │ ← 没有结论时这一行换成「预计 6.2k token」
│  新增 2 条，可更新                  │ ← note：一行灰字，≤18 字（方案 B，见 §13 S1.4）
│  ─────────────────────────────────  │
│  1. 白银大涨 7%，贵金属链集体走强   │
│     [[1312]] [[1301]]               │ ← 引用可点，跳回原文并高亮
│  2. 德福科技 2 亿回购，回购潮延续   │
│     [[1298]]                        │
├─────────────────────────────────────┤
│ [今日热点] [英伟达] [A股异动]        │ ← chips = 切换模板 id，切完只重新报价
│ 加个关键词，例如「降准」       [↑]  │ ← Step 1 里它是追加检索词，不是自由问答
│ 本次约 3.2k token（全量 3.9k）      │ ← 价格跟着动作走，不能看起来像免费
└─────────────────────────────────────┘
```

|     | 主线             | 关键词          | 追问（点"展开"，Step 3） |
| --- | -------------- | ----------- | --------------- |
| 触发  | 点「生成 / 更新」     | 输入后按 ↑，**只重新报价** | 点某条主线           |
| 底层  | `hot-today` 模板 | 追加到模板关键词，参与检索与缓存键 | 主线结论 + 该条引用全文   |
| 上下文 | 当日全量           | 时间窗 + 关键词   | 上一次结果（threadId） |

**「今日主线」不是独立功能，是模板里的默认任务**（`brief: true`），因此不需要两套代码。

追问不需要工具循环：把该条引用的 2–4 篇全文 + 该条结论塞进下一次单次调用即可。

## 5. 数据模型

```sql
CREATE TABLE IF NOT EXISTS agent_run (
    id          TEXT PRIMARY KEY,       -- r_20261127T162012_a3f9
    kind        TEXT NOT NULL,          -- template | research | followup
    template_id TEXT,                   -- hot-today / nvda-bullish / a-share-drop
    params_json TEXT,                   -- {window:'1d', keywords:[], question:'...'}
    thread_id   TEXT,                   -- Step 3 会话记忆预留
    parent_run_id TEXT,                 -- 追问链
    trigger     TEXT NOT NULL,          -- 只允许 'user'
    trigger_by  TEXT NOT NULL,          -- 具体账号，审计用
    window_key  TEXT NOT NULL,          -- '2026-11-27'，跨天判定（见 10.2）
    strategy    TEXT NOT NULL,          -- full | delta（见 10.2）
    base_run_id TEXT,                   -- delta 所基于的 full run；full 时为 NULL
    watermark   INTEGER NOT NULL,       -- 生成时候选集的 max(news.id)
    status      TEXT NOT NULL,          -- running | succeeded | failed | rejected
    answer_json TEXT,                   -- {title, bullets[], insufficient}
    citations_json TEXT,                -- 校验通过的 id
    candidates  INTEGER,                -- 送进模型的条数
    tokens_in   INTEGER NOT NULL DEFAULT 0,
    tokens_out  INTEGER NOT NULL DEFAULT 0,
    model       TEXT,
    latency_ms  INTEGER,
    error       TEXT,
    created_at  INTEGER NOT NULL,
    finished_at INTEGER
);

CREATE INDEX IF NOT EXISTS idx_run_created ON agent_run (created_at DESC);
CREATE INDEX IF NOT EXISTS idx_run_brief   ON agent_run (kind, template_id, watermark);
-- 找"今天最近一次 full"是 delta 判定的第一步，单独建索引
CREATE INDEX IF NOT EXISTS idx_run_base    ON agent_run (template_id, window_key, strategy, status, created_at DESC);

-- 同一缓存键在 running / succeeded 两种状态下都只允许一行。
-- 只挡 succeeded 是不够的：那样两个请求都能插 running、都能调模型、都花钱，
-- 只有后写的撞索引作废 —— 钱已经花出去了（见 §10.9）。
CREATE UNIQUE INDEX IF NOT EXISTS uq_brief_active
    ON agent_run (template_id, window_key, watermark, params_json)
    WHERE status IN ('running', 'succeeded') AND kind = 'template';

-- 建索引前要把历史上"同键多条 running"收敛成一条，否则这条 DDL 会直接失败
-- （见 schema.sql 里的那条 UPDATE）
-- 旧索引必须显式删：CREATE INDEX IF NOT EXISTS 对同名老索引一个字都不改
DROP INDEX IF EXISTS uq_brief_key;
DROP INDEX IF EXISTS uq_brief_watermark;

CREATE TABLE IF NOT EXISTS agent_step (
    run_id      TEXT NOT NULL,
    seq         INTEGER NOT NULL,
    kind        TEXT NOT NULL,          -- llm | guard | error
    prompt_chars INTEGER,
    raw_output  TEXT,                   -- 截断存 ≤4KB，用于回放
    tokens_in   INTEGER,
    tokens_out  INTEGER,
    latency_ms  INTEGER,
    error       TEXT,
    ts          INTEGER NOT NULL,
    PRIMARY KEY (run_id, seq)
);
```

四个刻意的决定：

| 决定                                             | 理由                                       |
| ---------------------------------------------- | ---------------------------------------- |
| 部分唯一索引挡**重复写**                                  | 两个请求同时通过应用层检查时，第二个被数据库拒绝。注意它挡不住"第二个也调了模型"——那需要把 `running` 也纳入索引，见 §10.9 |
| `trigger` 只允许 `user`                           | 将来任何"定时预热"的改动都会在这里失败                     |
| `raw_output` 截断存                               | 磁盘 40G；存完整版会和"模型实际看到的截断版"不一致，排查时误导       |
| `window_key` / `strategy` / `base_run_id` 现在就建 | 增量更新（见 10.4）需要它；SQLite 加列要重建表，宁可先建着      |

## 6. 模板规范

单一文件 `prompts/agent/templates.md`，`## <id>` 分段，头部元数据 + 正文提示词。维护方式与现有 `prompts/analyze-news.md` 一致：改完重启生效，不重新编译。

```md
## hot-today
title: 今日财经新闻热点汇集
brief: true
window: 1d
keywords: []
min-hits: 5
expand-to: 3d
cost-hint: 约 0.4–1.5 万 token   # 按当日条数实算（11-12 是 0.43 万、11-16 是 1.43 万）

## system
你只能依据 <news> 标签内的内容作答。每条结论必须用 [[id]] 标注来源。
不得使用训练知识断言任何事实（财报、股价、政策原文一律不许）。
每条结论一句话，说清「什么事 + 意味着什么」。检索不到就说检索不到。

## user
以下是 {{from}} 至 {{to}} 的 {{count}} 条电报：
<news>…</news>

提炼 3–5 条主线，每条给 2–4 条引用 id。只输出 JSON。
```

### 6.1 三个内置模板

| id                     | 时间窗     | 关键词（OR）                        | `min-hits` | 主题锚点 `topic` / `min-topic-hits` | 可缓存             |
| ---------------------- | ------- | ------------------------------- | ---------- | ------------------------------- | --------------- |
| `hot-today` 今日热点汇集     | 1 天     | 无                               | 5          | 无                               | ✅ `brief: true` |
| `nvda-bullish` 英伟达利好   | **7 天** | 英伟达/NVDA/黄仁勋/算力/GB200/H100/台积电 | 2          | 无                               | ✅               |
| `a-share-drop` A 股异动归因 | 1 天     | 暴跌/大跌/重挫/跳水/回调/杀跌               | 3          | 沪指/上证/创业板/A股/两市… 至少 3 条         | ✅               |

「可缓存」= 这个模板的结果能当浮层首屏、参与水位线与增量判定。三个内置模板都满足；将来若有"每次都必须新生成"的模板（比如带随机性的冷启动选题），置 `brief: false` 即退出缓存与增量体系，每次都是 `strategy='full'`。

**关键词是 OR 不是 AND**。`keywords: [暴跌, 大跌, 重挫]` 里任何一个命中即取回该条；串成 AND 会得到 0 条。这个字段在 S1.2 早期是"解析了但没人用"，结果 `a-share-drop` 实际喂给模型的是当天**全部 139 条**，模型忠实地挑了两条美股下跌交卷。已修，并用测试钉住（`templateKeywordsNarrowRetrieval`）。

`a-share-drop` 必须多两条硬约束：

1. 库里没有指数数据，只能回答"新闻里有多少条在讲下跌"，**不能断言"今天暴跌了"**（写在 system 里）。
2. 检索是字面匹配，"跌"会把美股个股、土耳其银行、DRAM 合约价一起捞进来。所以它多一道主题校验：候选里提到 `topic` 锚点的条数不足 `min-topic-hits` 就拒答，**0 成本**。

主题校验的判据刻意简单 —— 只数"标题或正文里有没有出现锚点词"，不做语义判断。理由是**便宜且可解释**：拒答时必须能说出"3 条里只有 2 条提到沪指"，而不是一句"相关性不足"。实测 2026-11-27：全天 169 条，提到下跌的只有 3 条，其中 2 条带锚点 → 差一条，拒答。改成这个之前，同一批数据花了 1.1 万 token 得到两条美股结论。

### 6.2 输出契约

```json
{
  "title": "今日主线",
  "bullets": [
    { "text": "白银大涨 7%，贵金属链集体走强", "refs": [1312, 1301] }
  ],
  "insufficient": false
}
```

服务端处理顺序：解析 JSON → 校验 `refs` ⊆ 候选集 → 丢弃 `refs` 为空的条目 → 若全部被丢则整次标 `rejected`。

## 7. 检索与预算

### 7.1 取数：全量捞进内存，排序不放 SQL

```sql
SELECT id, title, content, publish_time, level, analysis_json
FROM news
WHERE publish_time >= ? AND publish_time < ?
  AND (? IS NULL OR title LIKE ? OR content LIKE ?)   -- LikePattern 转义，复用现有工具
```

不 `LIMIT`。600 行 × 约 200 字符 ≈ 120KB，全量进内存毫无压力；打分与截断放 Java，因为规则要可测试、可调，不该埋在 SQL 里。

> **勘误：原设计里的 `ORDER BY (level='A') DESC` 是无效代码。** 实测全库 1137 条，level 只有 `B`（112）和 `C`（1043），**A 级 0 条**。这条排序等于没写，必须换成下面的打分。

### 7.2 分类与合并（先分类，再打分）

全库 1157 条实测分布，决定"该删什么、该压什么"：

| 类别                                | 条数  | 占比    | 判定                    |
| --------------------------------- | --- | ----- | --------------------- |
| 栏目引流 `【风口研报】`/`【盘中宝】`/`【掘金行业龙头】`… | 37  | 3.2%  | 真无效，剔除                |
| 行情播报（指数/期货/现货 + 涨跌 + 数字）          | 105 | 9.1%  | **不是无效，是低密度**，合并后只给标题 |
| 正文 <40 字                          | 135 | 11.7% | 信息在标题，只给标题            |
| 海外非财经（军舰/总统/大选/袭击）                | 13  | 1.1%  | 降权不删                  |
| 完全重复标题                            | 5 组 | —     | 合并                    |

**结论：真正该删的只有 3.2%。** 过滤的价值不在"排噪"，而在**避免把正文预算花在 30 字的行情播报上**——所以它是分层打包的前置，不是独立功能。

```java
enum NewsClass { PROMO, QUOTE, TERSE, OVERSEAS, NORMAL }
```

| 类          | 判定（结构特征，非主题词）                    | 处理       |
| ---------- | -------------------------------- | -------- |
| `PROMO`    | **标题以 `【` 开头**（不限栏目名）            | **全部剔除** |
| `QUOTE`    | 含「指数/期货/现货/ETF」+ 涨跌词 + 数字，且无公司主体 | 合并，强制 L2 |
| `TERSE`    | `len(content) < 40`              | 强制 L2    |
| `OVERSEAS` | 军舰/总统/大选/袭击，且无财经词                | 打分 −2    |
| `NORMAL`   | 其余                               | 正常打分     |

**`PROMO` 为什么不用栏目白名单**：实测 18 个栏目、37 条，`【` **100% 出现在标题首位**（非开头 0 条），且非括号形式的导流特征（"这家公司/布局了/机构调研"）为 0 条。所以判据用前缀就够，新栏目自动覆盖，不用维护名单。

代价要认：37 条里约 13 条其实有内容（`【电报解读】`3、`【机构调研】`3、`【研选·数据】`4、`【财联社早知道】`1、`【九点特供】`1、`【玩转ETF】`1），一律删掉等于每天少 1–2 条信息。补偿手段：过滤时按栏目名计数打日志，出现高频新栏目或疑似误杀时能立刻发现。

#### 已落地：同一个判据也用在「分析」按钮上（2026-11-27）

列表**照常展示**这些条目（用户仍可能想看原文），但点「分析」会直接被拦——因为导流条正文是荐股话术，判它必然得出"利好某某板块"，等于花钱买一句广告。

三处实现，判据全部来自 `NewsClass.isPromo(title)`（`ai/NewsClass.java`），只有一份定义：

| 位置                            | 行为                                                        |
| ----------------------------- | --------------------------------------------------------- |
| `NewsClass.isPromo`           | 唯一判据：`title.startsWith("【")`，纯静态、可单测                      |
| `AnalysisService.analyzeNews` | 在 `isFresh` 之后、配额判断**之前**拦住，抛 `400 / PROMO_ITEM`；不调模型、不记账 |
| `useNewsFeed.analyze`（前端）     | 先判一次直接弹提示，**不发请求**；catch 里遇 400 不把按钮改成"重试分析"              |

位置的两个细节都有理由：拦在 `isFresh` 之后，历史上已分析过的导流条仍能取到缓存（不能因为新规则把旧结果藏掉）；拦在配额判断之前，被拦的这条不扣次数、不占别人额度。

由 `PromoSkipTest` 4 条守住：拦截时模型调用 0 次 / 缓存仍可取 / 正常条目不被误杀 / `【` 不在首位不拦（用 `contains` 会误杀大量引用式标题）。


**合并规则**：同「标的 + 方向」的连续播报（如「恒生科技指数跌幅扩大至 2% / 3% / 4%」）只留幅度最大或时间最新的一条，标题标注 `（当日 N 次播报）`。

> **实测修正**：原文写"105 条里 23 组重复、涉及 66 条"，那个数是**跨天**分组算出来的，而检索窗口是单日 —— 跨天的重复根本不会出现在同一次 run 里。按"同一天"口径重算，全库只有 **8 组、约 17 条**：韩国 KOSPI 一天 3 次（11-12、11-23）、恒生科技跌幅 2 次（11-13）、美股股指期货 2 次（11-23）、土耳其银行指数 2 次（11-27）等。
>
> 所以合并的真实收益是：**11-12 合并 1 条、11-13 合并 2 条；11-16 和 11-27 都是 0 条**。它不是每天都省的常规优化，而是"偶发刷屏"的兜底 —— 一天被同一标的播 9 次时，没有它就是 9 条挤占正文额度。价值真实，但别指望它显著降 token。

> 反例警示：不能拿关键词当黑名单。"英伟达"既可能出现在正常新闻里，也可能出现在引流栏目里 —— 判据必须是**结构特征**（`【` 前缀），不是主题词。

### 7.3 打分（确定性、可单测、不花钱）

| 信号            | 分值 | 例子                     |
| ------------- | -- | ---------------------- |
| 金额 / 数量 / 百分比 | +3 | 2 亿元、装机 10GW、上涨 7%     |
| 公司行为动词        | +3 | 回购、增持、中标、签约、收购、停牌、业绩预告 |
| 政策与宏观         | +2 | 降准、降息、关税、补贴、监管、央行      |
| 市场异动          | +2 | 涨停、跌停、暴涨、暴跌、创新高        |
| 海外龙头 / 指数     | +1 | 英伟达、特斯拉、美联储、纳指         |
| 纯评论无数字        | −1 | 「分析师认为…」               |

`score ≥ 3` 进 L1（给正文），否则 L2（只给标题）。同分按时间倒序。

### 7.4 分层打包：600 条也做得动

| 层  | 内容                | 上限   | 常规日 88 条 | 忙碌日 241 条 | 满负荷 600 条  |
| -- | ----------------- | ---- | -------- | --------- | ---------- |
| L1 | 标题 + 正文（截 1200 字） | 80 条 | 约 25 条   | 约 50 条    | 80 条（按分数截） |
| L2 | 仅标题 + 时间          | 不限   | 约 63 条   | 约 191 条   | 约 520 条    |

依据：**标题平均 28 字、正文平均 170 字，标题只占全文 14%**。电报的正文多为背景复述，标题已含「主体 + 动作 + 数字」。

prompt 里必须如实说明分层：`共 600 条，其中 80 条含正文、520 条仅标题`。这句话直接影响模型敢不敢下结论，比任何「请谨慎」都有效。

### 7.5 预算对照（S1.1 实测，2026-11-27）

下表「分层后」一列全部来自 `PackProbe` 对真实库的实测，不是估算：

| 场景  | 日期    | 条数  | 全正文   | 分层后        | 剔除 | 合并 | L1 / L2  |
| --- | ----- | --- | ----- | ---------- | -- | -- | -------- |
| 常规日 | 11-27 | 119 | 1.4 万 | **0.94 万** | 0  | 0  | 52 / 67  |
| 常规日 | 11-12 | 101 | 1.2 万 | **0.43 万** | 4  | 1  | 22 / 74  |
| 偏忙  | 11-13 | 209 | 2.4 万 | **1.11 万** | 7  | 2  | 53 / 147 |
| 最忙  | 11-16 | 241 | 2.8 万 | **1.43 万** | 6  | 0  | 80 / 155 |
| 满负荷 | 造数    | 600 | 7.0 万 | **2.5 万**  | —  | —  | 80 / 520 |

三处与设计预估不同，都以实测为准：

- **行前缀真实 21 字，不是 17 字**：`[[1312]] 11-27 14:32 ` 拆开是 `[[`2 + id 4 位 + `]]`2 + 空格 + 时间 11 + 空格。S1.1 定的 17 只覆盖了 **id 之外**的部分，id 位数被漏掉（600 条 × 4 位 ≈ 2400 字 ≈ 1400 token）。S1.2 已把口径改成 `17 + id 位数`，并由 `PromptBuildTest` 直接断言「拼接长度 == 预估长度」——两处再分叉，构建立刻红。
- **L1 占比比预估高**：常规日 40–44%（52/119），而不是 28%。原因是"回购/中标/增持"这类标题命中率高，一天能有三四十条 —— 这是好事，说明正文额度没浪费在无关条目上。
- **导流剔除量低于 3.2% 的平均值**：单日 0–7 条。11-27 一条都没有，说明栏目导流不是每天都有。

> 7 万 token 在 128k 窗口里**装得下，但不该装**：成本 6 倍、首字节 5–15 秒、模型注意力被稀释后主线会退化成泛泛之谈（这个损失用 token 数衡量不出来）。**能不能装下是窗口问题，该不该装是质量问题。**

| 参数               | 值          | 说明                                  |
| ---------------- | ---------- | ----------------------------------- |
| `max-tokens-in`  | 30000      | 硬闸：超了先把 L1 尾部降级为 L2，降级仍不够才丢弃 L2 最早的 |
| `max-tokens-out` | 900        | 5 条主线远小于此                           |
| 单条正文上限           | 1200 字     | 超长截断并标注                             |
| `context-window` | 128000（可配） | Step 1 就要探测，不能等 Step 2              |

### 7.6 token 预估（给用户看）

```
est = [ Σ_L1 (17 + digits(id) + len(title) + 2 + min(len(content),1200))
      + Σ_L2 (17 + digits(id) + len(title) + 1) ] / 1.7 + 400
```

- `17` = 行前缀里 **id 之外**的部分：`[[` 2 + `]]` 2 + 空格 + `MM-DD HH:mm` 11 + 空格
- `digits(id)` = id 的位数（4 位 → 前缀 21 字，5 位 → 22 字）
- `2` / `1` = 换行：L1 是「标题后 + 正文后」两个，L2 是「标题后」一个

**S1.2 复核结果（2026-11-27，真实库三天）**：拼接字符数与逐条累加**完全相等，偏差 0 字 / 0 token**。

| 日期 | 条数 | L1 / L2 | 真实拼接字符 | token 预估 | 偏差 |
|---|---|---|---|---|---|
| 11-27（18:10 复核） | 129 | 56 / 73 | 16911 | 10348 | 0 |
| 11-16 | 241 | 80 / 155 | 24020 | 14530 | 0 |
| 11-13 | 209 | 55 / 145 | 18881 | 11507 | 0 |

口径之所以能对齐，是因为把「预估」和「拼接」交给了同一份代码：`PromptBuilder.line()` 生成字符串、`PackedNews.promptChars()` 算长度，`PromptBuildTest` 断言 `line(p).length() == p.promptChars()`。两边任何一处改动而没同步另一处，测试立即红。

**预估必须比实际略高，不能比实际低** —— 它是硬闸的依据。按 8 字算出来的闸门，实际会漏掉四成 token，那这个闸就没拦住任何东西。

| 方法   | 路径                     | 说明                                    |

| GET  | `/api/agent/templates` | 模板列表（id/标题/窗口/关键词/min-hits/成本量级）      |

`precheck` 是"打开浮层不花钱、但要让人知道点下去花多少"的落点：只做分类/合并/打分/水位线比对，**不调模型、不写库**。

```json
GET /api/agent/precheck?templateId=hot-today&keywords=

      "reason": "新增 5 条，带旧结论只发增量",   // 排查用，界面不读

      "newCount": 5,              // full 之后新增的候选条数
      "candidates": 63,
      "estimateTokens": 3221,

      "remaining": 99,
      "note": "数据没有变化，直接返回上一版", "detail": null }
```

```json
200 { "status": "rejected", "reason": "min-hits",

```

三条与早期草案的差异，都是落地时改的：

| 项 | 早期草案 | 现在 | 为什么 |
|---|---|---|---|
| `meta.newCount` | 有 | **没有** | 浮层在点之前已经从 `precheck` 拿到这个数；两处都给会出现两个来源，且 `Result` 里本来就没有这个字段 |

### 9.1 `/api/agent/health`：和 `/healthz` 不是一回事

| | `/healthz` | `/api/agent/health` |
|---|---|---|
| 回答 | 进程还活着吗 | 主线现在能不能干活、卡在哪一步 |
| 鉴权 | 匿名（`permitPaths`） | 要令牌；`guest` 403，`rw` / `ro` 可读 |
| 状态码 | 库读不出来 503 | 同上；**DEGRADED 仍是 200** |
| 用途 | 容器探针 / 负载均衡 | 人排查，或监控按分钟打 |

两者会给出**相反**的结论，这是设计而不是缺陷：key 过期时进程百分之百健康，主线一条都出不来。所以 DEGRADED 刻意不配 503 —— 接上探针只会让容器为一个过期的 key 反复重启，而重启治不好 key。

```json
GET /api/agent/health

200 { "status": "UP",              // UP | DEGRADED（DOWN 只在库读不出来时，配 503）
      "enabled": true,
      "templates": { "count": 3, "ids": ["hot-today", "nvda-bullish", "a-share-drop"],
                     "error": null },     // 加载失败的原因，正常为 null
      "llm": { "ready": true, "model": "deepseek-flash", "timeoutMs": 60000 },
      "today": { "succeeded": 3, "failed": 1, "rejected": 0,
                 "tokensIn": 32000, "tokensOut": 4800 },
      "quota": { "dailyCap": 100, "guestDailyCap": 5, "used": 3, "remaining": 97 },
      "running": { "count": 0, "oldestAgeSec": 0, "staleSeconds": 180, "stuck": 0 },
      "problems": [] }             // 人能直接读的原因；空数组即 UP
```

四个刻意的取舍：

- **不真调一次模型**。那样每被监控打一次就烧一万 token，体检本身成了账单主项。`llm.ready` 只表示 key 在，连通性由第一次真实调用暴露，原因写进 `markFailed` 的 `error` 列。
- **`problems` 是数组不是一句话**。「关掉了 + key 也没配」拼成句子必然漏一半，而这两种故障的修法完全不同。
- **`running.count > 0` 不算问题**。生成途中打体检是常事，判据是 `oldestAgeSec > staleSeconds`，那时 `stuck` 才会 > 0。
- **不回显 key / base-url**。体检结果会跟着截图、工单、群消息流出去，它是诊断不是配置转储；CI 里有一条 `grep -qi 'sk-'` 守着。

**权限**（与单条分析同一套角色，实现在 `BasicAuthFilter` + `Roles`）：

| 角色 | `templates` / `precheck` / `runs` | `ask` | `health` |
|---|---|---|---|
| rw | ✅ | ✅ | ✅ |
| guest | ✅ | ✅（受 `app.agent.guest-daily-cap`，默认 5） | ❌ 403 |
| ro | ✅ | ❌ 403 | ✅ |

只读账号能读到已有结论，但它"不产生花费"的定义不能破。游客放行是因为 `guest-daily-cap` 这个配置项本来就是为它配的 —— 白名单里不许，那个数字就永远不生效，而界面上却显示游客也能生成。`health` 反过来只挡游客：它报的是全站 token 消耗、key 有没有配、有没有僵死的 running 行，是运维视角；而它对 `ro` 无害（纯读、0 成本），挡了反而让"只读账号不能执行这个操作"这句拒绝文案变成假话。

**为什么同步不流式**：单次调用 5–10 秒，前端 loading 足够；流式要多一套 SSE + 小程序轮询两套逻辑，收益不抵成本。

## 10. "重复分析"怎么处理：三档策略

### 10.1 先把两个问题分开

"重复分析今日主线"其实是两件不同的事，混在一起会设计错：

| # | 现象           | 代价                | 处理                  |
| - | ------------ | ----------------- | ------------------- |
| 1 | 数据没变，用户又点了一次 | 全量重跑，白花 1 万 token | **缓存命中**，0 成本（10.3） |
| 2 | 数据变了，但只多几条   | 全量重跑 88 条，也花 1 万  | **增量更新**（10.4）      |

第 1 个是原来的设计就能解决的。第 2 个才是真问题——电报是持续采集的，一天 88–241 条，用户任何时刻点开，水位线几乎总是比上次新。如果每次都全量，一天点 3 次就是 3 万 token。

### 10.2 判定流程

```
候选集（今日，已过 7.2 分类/合并 → 7.3 打分）→ 当前 watermark W
 │
 ├─ ① 跨策略缓存比对：查今日该模板最近一次 succeeded 的 run（full 或 delta 都算）
 │    └─ 存在且 watermark == W   → 缓存     数据没动，0 成本
 │
 └─ ② 找 base：今日最近一次 succeeded 的 full run F（idx_run_base）
      ├─ F 不存在                → full     今天第一次，或者只有失败记录
      ├─ F.window_key ≠ 今天      → full     跨天，旧结论整份作废
      ├─ 新增 n = 候选(id > F.watermark).size
      │    ├─ n < 3              → 缓存     返回 F，提示"新增 n 条，未达重算阈值"
      │    ├─ 3 ≤ n ≤ 65         → delta    带旧结论，只发增量正文
      │    └─ n > 65             → full     增量已不划算
      └─ 同日 delta 已 3 次       → full     防结论逐代漂移
```

**① 为什么必须排在②前面（这是原设计的缝）**：缓存键里含 `watermark`，而 delta 成功后会把它推进到新的 W。假设 10:00 跑了一次 delta（W 从 1300 → 1312），11:00 用户再点：

- 旧写法先查"最近一次 **full** 的 F"，两者比较的是 `W == F.watermark`，即 1312 vs 1300 —— 不等，于是继续往下算出 n，再跑一次 delta。
- 但这时数据一个字没变（W 仍是 1312）。用户看到的是"数据没变，点一次又被扣钱"。
- 「同日 delta 满 3 次强制 full」能兜住成本上限，兜不住这个体验。

所以缓存比对必须**跨策略**：full 和 delta 的输出形态完全一样（都是完整 3–5 条主线），对"数据没变就复用"这件事是等价的。只有没命中缓存时，才需要去找 base full。

**① 命中后不要再判 guard**：同一批数据已经有结果了，"材料够不够"这个问题已经被上一个请求回答过。反过来（先 guard 后缓存）会出现"昨天成功过一次的数据，今天因为 guard 改了阈值而被拒答"，用户点开看到的是拒答而不是已经生成好的主线。

三个阈值都有出处，不是拍的：

- **n < 3 走缓存**：为 1–2 条新闻花 6000 token 换一次重排，性价比为负。界面显示"新增 2 条 · 可手动刷新"，把决定权给用户。
- **n > 65 走 full**：这是算出来的交叉点。L1 上限 80 条，所以 full 成本随总量是**缓增**（只有 L2 标题在涨）：`16544 + 38n` 字；delta 固定部分 `8644` 字 + 新增正文 `166n`。解 `16544 + 38n = 8644 + 166n` 得 n ≈ 62，取 65 留余量。Step 1 落地时用真实数据校准这个常数。
- **delta ≤ 3 次**：见 10.4 的"不链式"。

### 10.3 缓存键：四个都要对

```
template_id + window_key + watermark + params  四者全等 才算命中
```

少任何一个都会出错：

- 漏 `window_key` → 昨天的 full 被当成今天的。这个 bug 不是理论问题：某天采集一条没进来时，今天和昨天的 `max(news.id)` 完全相同，旧写法会直接返回昨天的结论。
- 漏 `template_id` → 「英伟达」的结论被当成「今日热点」的。
- 漏 `params` → 同一模板带不同关键词是两次不同的检索。不带这一列时，一次带自定义关键词的 run 会把这个水位线的缓存占住，后续用模板默认关键词的请求拿到别人的答案。

**并发防护的三层（2026-11-28 已全部落地）**

| 层 | 实现 | 挡住什么 |
| --- | --- | --- |
| ① 缓存比对 | 应用层，跨策略 | "连点"：第二次直接命中缓存，0 成本 |
| ② 进程内单飞 | `SingleFlight`（`Future`） | 同进程的两个并发点击：合并成一次调用，第二个等第一个的结果 |
| ③ 唯一索引 | `uq_brief_active`（含 `running`） | 跨进程 / 跨重启：第二个请求 `INSERT` 就失败，**还没调模型就省了钱** |

三层各管一段，缺一层都有明确的漏：只做 ① 真并发双花；只做 ② 多副本时静默失效；只做 ③ 第二个请求只能轮询或 503。

索引名从 `uq_brief_watermark` 改成 `uq_brief_key` 而不是原地改：`CREATE INDEX IF NOT EXISTS` 对已存在的同名索引一个字都不会改，老库永远升不上来。所以用"先建新索引、后删旧索引"的两步（顺序反过来会有一个"没有任何唯一约束"的瞬间），两条语句都幂等，`spring.sql.init.mode=always` 每次启动重跑无害。

### 10.4 增量更新：换的是输入，不是答案

**你的直觉（在旧结果上加增量）方向是对的，但不能做成"在旧答案上打补丁"。**

原因是：主线是**全局重排**的产物。"白银大涨 7%"这条新消息进来，可能让贵金属从第 4 升到第 1，也可能让原来两条独立主线（"贵金属走强"和"有色反弹"）合并成一条。只喂增量，模型看不到旧的完整排序依据，只能局部修补，最后输出「今日新增：1. 2. 3.」——那是增量播报，不是今日主线。用户点开想看的是"今天整体什么情况"。

所以增量的正确语义是：**省掉旧条目的正文预算，但输出仍然必须是完整的 3–5 条主线。**

**输入结构**（三段，标签隔开）：

```xml
<previous>
上一版结论（16:20 生成 · 当时 88 条 · 共 5 条主线）
1. 白银大涨 7%，贵金属链集体走强  [[1312]] [[1301]]
2. 德福科技 2 亿回购，回购潮延续  [[1298]]
…
</previous>

<previous_titles>
当时全部 88 条的标题（仅标题，无正文）
1312 | 10:12 | 现货白银涨7%，创三年新高
1301 | 10:05 | 沪银主力合约涨停
…
</previous_titles>

<previous_evidence>
上面 5 条主线引用到的 20 条原文（用于核对旧结论是否还成立）
[[1312]] 现货白银日内涨幅扩大至7%…
</previous_evidence>

<new_news>
16:20 之后新增 12 条（8 条含正文，4 条仅标题）
1450 | 16:41 | 湖南黄金：拟收购…
…
</new_news>

要求：输出**完整的今日主线**（3–5 条），不是增量列表。
旧主线如因新消息不再成立，可删除或改写，但要在 dropped 里说明原因。
引用只能来自上面出现过的 id。
```

三段各有用处，缺一不可：`previous` 给结论、`previous_titles` 给全貌（否则模型不知道当时还有哪些没进主线的条目）、`previous_evidence` 给证据（否则它判断"这条旧主线还成不成立"只能靠猜，容易照抄）。

`previous_evidence` 取**旧主线 refs 去重后的前 20 条**，超出部分退回只给标题——这是成本闸：不设上限时，5 条主线 × 平均 5 个引用就能把整份正文又塞回去，增量就白做了。

**base 永远指向 full，不链式。** 这是关键决定：

```
扁平（采用）  delta3 ← full ＋ full 之后全部新增（12+15+8=35 条）
链式（不用）  delta3 ← delta2 ← delta1 ← full
```

链式成本最低，但每代都在上一代结论上再压缩一次，三代之后主线会退化成"市场情绪偏暖"这类正确的废话，而且上一代编错的引用会被继承下来、再也纠不回来。扁平方案的误差永远只有一代，代价是累计新增变多——而这正好由 `n > 65 走 full` 兜住。

### 10.5 成本对照（88 条基数，实测 28 字标题 / 170 字正文）

| 场景             | 字数    | token   | 对比 full        |
| -------------- | ----- | ------- | -------------- |
| full（88 条）     | 17644 | ≈ 10380 | —              |
| delta（新增 12 条） | 10460 | ≈ 6150  | **省 41%**      |
| delta（新增 40 条） | 15604 | ≈ 9180  | 省 19%          |
| delta（新增 65 条） | 19954 | ≈ 11740 | 基本持平 → 改走 full |
| 缓存命中           | 0     | 0       | 省 100%         |

按当前采集节奏（每小时 3–10 条），绝大多数点击落在"新增 3–15 条"这一档。

**2026-11-28 实测（真实库 11-27，140 条候选，5 条主线 × 3 引用，不调模型）**：

| 新增 | 全量 token | 增量 token | 省 |
|---|---|---|---|
| 1 条 | 10888 | 7072 | 35% |
| 29 条 | 10888 | 8073 | 26% |
| 59 条 | 10888 | 9533 | 12% |

**实测比上面那张推算表低 5–15 个百分点，原因是 `previous_titles`。** 140 条标题每条约 40 字符 = 5600 字符，这部分开销与"新增几条"完全无关。新增越少，它占总成本的比例越高 —— 所以增量的收益上限取决于**新增条数占总数的比例**，而不是新增条数的绝对值。推算表里那个 41% 是按 88 条基数、12 条新增、28 字标题算的；真实数据标题更长、基数更大。

这也顺带验证了 `n > 65` 这个阈值：59 条时还省 12%，65 条约省 10%，再往上就趋近于零 —— 交叉点确实在 60 附近，取 65 留余量是对的。

**省得不多，但首字节的差别是实打实的**：7000 token 的 prefill 约 1–2 秒，1.1 万约 2–4 秒。

**所以还要一道真实成本闸（2026-11-28 加）**：`Strategy` 判完 DELTA 之后，`prepare` 会把两种提示词各渲染一遍，谁短用谁。

```java
int fullChars  = PromptBuilder.render(t, pack, from, to).length();
int deltaChars = PromptBuilder.renderDelta(...).chars();
if (deltaChars >= fullChars) → 改走全量，note 里说明原因
```

理由是一次实测：今天 60 条候选、新增 3 条时，增量 7501 字符 vs 全量 5836 —— **增量贵 29%**。总量没到 L1 上限（80 条）时全量里每条都有正文，而增量要额外付 57 条旧标题 + 15 条证据正文，省下的 3 条新增正文根本抵不过。

**是否划算取决于"证据链长度 + 旧标题量"与"省下的新增正文"之比，不是新增条数。** 这个比例在判定阶段算不出来（要渲染才知道），所以直接渲染两遍比长度 —— 几毫秒，比错发一次请求便宜三个数量级。`n < 3` 那一档仍然保留：它为 1–2 条新闻连渲染都不必做。

### 10.6 增量特有的三条护栏

| 风险             | 护栏                                                                |
| -------------- | ----------------------------------------------------------------- |
| 旧结论的引用被误判为"伪造" | 引用校验的白名单要包含 `<previous_titles>` 里的全部 id，不只是本次新增的                  |
| 模型把主线全删了重写     | 输出 `dropped` 逐条说明理由；若 5 条全 dropped 且新增 < 5 条，判 `suspect` 并回退到缓存结果 |
| 旧结论本身有错，增量会继承  | `previous` 只作为参考不写成"必须保留"；每次仍做一次完整引用校验                            |

| -------------------- | ------ | ---------------- |

| guard 拒绝             | 不扣     | 0（没调模型）          |

| 每日 token 硬上限         | —      | 触顶后拒绝新请求，防失败重试刷钱 |

### 10.9 并发单飞：A + B 已落地（2026-11-28）

问题：一次生成 6–10 秒，这期间同一 `(template_id, window_key, watermark, params)` 的第二次点击如果也进了"调模型"，就是两份一万 token。只挡 succeeded 的唯一索引只能让后写的作废 —— 钱已经花了。

**先排除的方案 C（数据库行锁 / `BEGIN IMMEDIATE`）**：SQLite 的写事务是全库串行的，拿它当锁等于让所有写操作排队，收益和 A 相同、代价大得多。

**A：`running` 也纳入唯一索引（负责正确性）**

```sql
CREATE UNIQUE INDEX uq_brief_active
    ON agent_run (template_id, window_key, watermark, params_json)
    WHERE status IN ('running', 'succeeded') AND kind = 'template';
```

这是唯一的**跨进程**保证：第二个请求在 `INSERT` 那一刻就失败，一分钱不花，且不依赖任何进程内状态。

落地时的三个细节，每个都对应一次真实的坏结果：

1. **僵尸占用必须能释放。** `running` 行就是锁，进程被 kill 后它留在库里。`resetStuck()` 只在启动时跑，挡不住运行期被 kill 的情况 —— 不清理的话，一次崩溃就把这个水位线永久锁死，之后每次点击都 503 直到重启。所以 `claim()` 在插入失败后会看那条 running 的 `created_at`：早于 `stale-seconds`（默认 180 秒，约等于模型超时的三倍）就标 failed 再抢一次。用条件更新（`WHERE status='running' AND created_at <= ?`）而不是先查后改，避免两个进程同时"释放"同一条。
2. **拒答不能走 `running` 那条路。** guard 拒答是 0 成本的结论，但此刻可能正有别人在跑同一批数据。如果拒答也先插 running，就会撞索引 → 用户拿到 500，而"今天新闻就少"这个事实被一个错误盖住了。所以 rejected 用 `insertRejected` 一步写终态（它不在索引条件里）。
3. **迁移前要收敛历史 running。** 老索引不管 running，库里可能已经躺着同键的多条 running，直接建新索引会失败。`schema.sql` 里先用一条 UPDATE 把它们标成 failed（保留最新一条），再建索引。

**B：进程内单飞（负责体验）**

`SingleFlight` 用一个 `ConcurrentHashMap<key, CompletableFuture>` 把同键的并发调用合并：leader 执行，follower 等它的结果（含异常）。

- follower 拿到的就是 leader 的结果，所以不需要再查一次库，也不会自己重试 —— **重试等于再花一万 token 撞同一个错**。
- 等待有上限（模型超时 + 5 秒）。超时上限必须比被等的事情长，否则必然先超时。
- key 必须和缓存键**同构**：少一个维度，本该分开的两次生成会互相顶掉；硬要合并不同的 key，用户会拿到别人关键词的结果。
- 为什么不用 `synchronized` / 每 key 一把锁：锁只能串行化，第二个请求拿到锁后还得自己判断"是不是已经有结果了"，这段判断就散落在两处；Future 直接把结果交过去。

**为什么 A+B 都要有**：只做 B，多副本时锁静默失效且不报错（最坏的一种正确性）；只做 A，第二个请求只能轮询或 503。B 负责"等结果"，A 负责"不重复花钱"。

**残留风险（认了，写在这里）**

- BUSY 分支的等待会占着请求线程（上限 `busy-wait-ms`，默认 15 秒）。单实例下几乎不触发。
- `stale-seconds` 给 180 秒：如果模型真的挂住超过三分钟没返回、进程又还活着，会被误判成僵尸并再跑一次。代价是一万 token，概率取决于供应商。要更保守就调大这个值，代价是崩溃后锁死的时间变长。
- 这套只管 `kind='template'`。Step 2 的 `research`（自由提问）**不该**共享生成权：同一个问题答案一样，但那是缓存该管的事，而缓存键对自由文本没意义。

## 11. 前端

- **不改 `pages.json`**：浮层是 `position: fixed` 组件，两端产物与导航都不变。
- H5 与小程序走**同一套接口**（同步 POST），不需要 EventSource。  
  |  |  |  |  
  | --- | --- | --- |
- 状态机：`idle → estimating（调 precheck）→ running → done | rejected | error`。
- 三处必须可见：点击前预估、结果元信息（条数/步数/token/生成时间）、失败原因（含检索条件）。
- **打开浮层只会调 `precheck`，永远不调模型**；有缓存就直接渲染缓存内容 + "16:20 生成 · 数据无新增"。

按钮文案按 `precheck.strategy` 变，不能一律写"生成"：

| strategy | 按钮       | 副标题                                             |
| -------- | -------- | ----------------------------------------------- |
| `cached` | 无需按钮     | 「16:20 生成 · 数据无新增」（或「新增 2 条，未达重算阈值 · 仍可刷新」）     |
| `delta`  | 「增量更新」   | 「新增 12 条 · 约 0.6 万 token（全量 1 万，省 41%）· 剩 96 次」 |
| `full`   | 「生成今日主线」 | 「首次生成 / 新增 78 条 · 约 1 万 token · 剩 96 次」         |

把 `baselineTokens` 一起显示，是为了让"省了多少"可核对——只写一个更小的数字，用户没法判断是真的省了还是模型降级了。

- `分析` 与 `问` 不合并：分析结果下方加一行「就这条继续追问 →」，自然导流。

**验收暴露的三个真问题（都已在代码里修掉两个）**：

1. **`max_tokens` 必须给 8000，不是 1200。** `deepseek-flash` 是推理模型，额度先被思考吃掉：给 1200 → `finish_reason=length`、正文一字未出；给 3000 → 同样截断（那次花了 1.4 万 token）；给 8000 → 成功，实际只用 1561（正文约 400 + 推理约 1100）。**同一输入两次的思考长度并不稳定**，所以上限要留足余量，不能卡着实际用量设。
2. **失败也要记 token。** 截断是 HTTP 200，钱已经花了，但异常路径原本把用量丢了、记成 `tokens_in=0`。已加 `LlmCallException` 携带 usage，`AgentService` 分两路 catch：能拿到 usage 的如实记，拿不到的（超时/401）记 0 不编造。
3. **`a-share-drop` 主题跑偏（未修，留给 S1.4 调）。** 关键词是「暴跌|大跌|重挫…」，检索按 `title LIKE OR content LIKE` 泛匹配，把美股个股、土耳其银行、DRAM 合约价都捞了进来；模型于是引用 `1164 Vertex制药美股盘前跌7.3%`、`1067 2028年DRAM合约价走跌风险` —— 措辞守住了「据电报」（防编造生效），但答的不是 A 股。花了 1.1 万 token 换来两条跑题结论。

| 7 ✅ | 编排接入 | `AgentService.ask` 的 ② 分支 + `generate` | `strategy` 与 `base_run_id` 写进 `claim`；**base 永远指向 full，不链式**（§10.4） |
| 8 ✅ | `DeltaStrategyTest` 11 条 + `BaseQueryTest` 6 + `DeltaPromptTest` 7 | 纯函数与查询测试，0 token | 阈值的两侧都测（2/3、65/66、2/3 次）、base 不会取到 delta、证据超限会裁、模板缺占位符会报错 |

**为什么放弃解析 `dropped`**：原设计想让模型在"删掉某条旧主线"时说明理由，据此判断是不是"全删了重写"。实现时发现两件事：一是 `dropped` 是模型的自述，它完全可以删了不说，判据变成"模型愿不愿意交代"；二是自述不可验证，和 P2（引用必须可验证）的原则冲突。改用**输出条数的相对变化**：`outBullets * 2 < baseBullets` 且新增 < 5 才判可疑。这条判据纯代码可算，且直接对应"用户看到的结论突然少了一半"这个真实症状。

**验收（§12.2 第 7–9 条，需真模型跑一次）**

- 新增满 3 条后点 → `strategy='delta'`、`base_run_id` 指向当天那次 full、`tokens_in` 落在 6000 上下（±30%），输出仍是**完整 3–5 条主线**，不是"今日新增：1. 2. 3."
- 连续 delta 三次 → 第三次的 `base_run_id` **仍指向最初那次 full**
- 第二天首次点击 → 必为 `full`，不会拿昨天的当缓存

**真模型验收（2026-11-28，两次调用约 1.6 万 token）**

场景：今天 60 条候选 → 跑 full → 插 3 条真实感新闻 → 再跑。

| 项 | 结果 |
|---|---|
| full | 57 条候选、5 条主线、14 个引用全部回查得到，3542 in / 2256 out |
| delta 首版 | **3 条主线，全部只引用新增的那 3 条**，旧的 5 条（美股大涨、黄金、霍尔木兹、美联储、并购）全部消失 |
| delta 修提示词后 | **5 条完整主线**：新增的 3 条被合并成一条"国内稳增长信号"，旧的 4 条保留，14 个引用全部可回查 |
| delta 成本 | 3770 in（full 是 3542）→ **反而更贵 6%** |

**验收逼出两个修正，都不是单测能发现的**

1. **模板缺"这是增量"的指令（已修）。** 首版输入结构全对、引用全真，但模型按 `<news>` 里只有 3 条的字面意思写 —— 正是 §10.4 明令禁止的"今日新增 1. 2. 3."。根因不是模型笨，是**任务描述与输入结构不一致**：模板还说"提炼今日主线"，而 `<news>` 的语义已经变成"只有增量"。加 `{{mode}}` 占位符，delta 时注入"输出完整主线、不是增量列表"。修完立刻变成 5 条。
2. **成本闸（已加）。** 单测里 9 条数据造 delta 是更短的，真实 60 条 + 15 条证据时反而贵 29%。见 §10.5。

#### S1.4 前置：note 怎么呈现（2026-11-28 已定，走方案 B）

做浮层之前先拿原型把这件事定了，因为它反过来约束后端文案。原型：`docs/proto/note-overlay.html`（纯静态，9 种真实场景 + 一条改前对照 / 深浅色 / 390·360·320 三档 / 行数实测）。

**结论：独立一行灰字，挂在 meta（`16:20 生成 · 88 条 · 5 条主线`）下方，不进 meta 行、不贴「刷新」按钮。**

| 位置 | 为什么不选 |
|---|---|
| 并入 meta 行 | note 一长就把「5 条主线」挤到下一行，结果和解释混成一片。实测 21 字就折行 |
| 贴「刷新」按钮 | 它解释的正是刷新为什么没生效，贴上去会被读成按钮的一部分 |
| 独立一行 ✅ | meta 只描述结果，note 只说这次动作；**没有 note 时整行不渲染**，不留空位 |

**按语义分两档颜色**（不是一种灰到底）：

| 场景 | 颜色 | 理由 |
|---|---|---|
| 数据无变化 / 未达阈值 / 走了增量 | `--dim` 纯灰 | 正常提示，不该抢主线内容的注意力 |
| 降级、回退（用户看到的是旧内容） | `--amber` + 前置圆点 + 「旧版」徽标 | "已回退上一版"这句话的读者其实在看旧结论，纯灰会被当装饰跳过 |

**宽度是接口契约，不是设计建议。** 标题区可用宽只有 290 / 264 / 224px（390/360/320，右边站着「刷新」），11.5px 下约合 25 / 22 / 19 个字。拿改前那批文案量出来的边界：

| 文案（改前） | 字数 | 390 | 360 | 320 |
|---|---|---|---|---|
| 新增 78 条，超过增量上限 65，全量更划算 | 20 | 1 | 1 | **2** |
| 新增 2 条，未达重算阈值（≥3），先看上一版 | 21 | 1 | 1 | **2** |
| 今日已增量 3 次（上限 3 次），这次回全量，防止结论逐代漂移 | 29 | **2** | **2** | **2** |

20–21 字在 320px 折行，19 字三档通吃，所以取 `Strategy.MAX_NOTE_WIDTH = 18`（往下留一格给字体渲染）。最后一行就是 `DELTA_LIMIT` 当时的原文——没人量过，它在代码里躺了一版。

这条上限写成可执行断言（`NoteCopyTest` 5 条）而不是注释：改文案改超了直接红，而不是等真机上看着别扭才发现。压完现文案全部 ≤16 字，三档屏宽都单行，「旧版」徽标同屏也不折。

**本轮随之改掉的实现**（都在 `note` 这条链路上）：

| 改动 | 原因 |
|---|---|
| `Strategy` 七句文案压到 ≤16 字，去掉日期与阈值 | 「上一版属于 2026-11-27」光日期就占 5 个字；过程量（`reason` / `added` / `deltaToday`）现在由 `prepare` 里新增的一行日志承接 |
| `Strategy.NOTE_SAME` 提成常量，两条缓存路径共用 | 跨策略比对直接命中那条**根本没走到 `decide`**，原来 `note` 传的是 `null` —— 用户最常见的"再点一次"恰好无话可说 |
| `AgentService` 三句降级提示提成常量（`NOTE_COST_GATE` / `NOTE_NO_PREV` / `NOTE_ROLLBACK`） | 内联字面量测不到；提出来 `NoteCopyTest` 才能卡宽度 |
| 骤减回退的 `note` 换成短句，带条数的长版本留在 `markFailed` 的 error 列 | 44 个字在浮层里折三行，把整块标题区顶变形；排查按 run 查 error 就够 |

**「强制重算」没做**：它要接口加 bypass 参数，且点击时必须提示"这一下要花多少"。现在有更便宜的出口——加一个关键词就换了检索与缓存键，必然重算。等真实使用中出现"我就是要在同一批数据上重跑"的需求再说。

#### 验收外的一处修复（2026-11-28）：key 只解析一次

验 S1.5 时起实例只为测「A 股异动拒答」，参数写的是 `--app.agent.api-key=sk-fake…`。主页面上点「分析」直接弹红字「大模型未就绪」—— 主线是好的，单条分析没有 key。

根因不是少配了一个参数，是**同一把 key 有两个入口**：`DeepSeekAnalyzer` 读 `analysis.api-key`，`DeepSeekAgentLlm` 读 `firstNonBlank(agent.api-key, analysis.api-key)`，各自调一次 `LlmCredential.find`。于是两种错法长得完全不一样：只配 agent 那份 → 主线好、分析挂；只配 analysis → 两处都好。同一个人按同一套心智模型操作，一半对一半不对。

改成 `ai/LlmKey`：启动时解析**一次**，两个消费方拿同一个对象，物理上不可能一半有一半没有。`forBaseUrl()` 保留唯一的分叉判据 —— auth.json 兜底来的官方 key 不发给非 deepseek 地址。`app.agent.api-key` 没删，降级为迁移别名：配了仍生效并打 WARN，两处不一致时以 analysis 为准并告警（静默分叉才是这里最贵的错）。

复现验证：只给 `--app.agent.api-key` 启动 → `analysisReady=true`、`/api/agent/health` 为 `UP`，启动日志两条消费者打的是同一个 key 与同一个来源。`LlmKeyTest` 5 条（共用同一实例 / 旧字段仍供分析 / 冲突取 analysis / auth.json 不发给中转 / 全无 key 降级），全量 185 → **190 绿**。
